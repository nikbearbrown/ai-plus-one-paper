# Learning architecture

## Outcomes
1. Given a feature brief, choose authored, deterministic procedural, offline generated or runtime generated content and justify the choice with constraints.
2. Build a playable authored baseline and trace a narrative change through a state graph with permitted transitions.
3. Import only candidate assets that pass a declared provenance, format, readability and engine compatibility check.
4. Design fixed tests for rejected candidates, timeout and missing-service cases; independently replay a fallback.
5. Compare two variants under the same scenes and acceptance rubric; report observed coverage, defects, timing and scope without inferring player preference.

## Progression
**Establish (1–2):** playable authored baseline, constraints and rights. **Build (3–6):** dialogue, art, world validation and bounded runtime. **Apply (7–8):** playtest and handoff. One original game case, *Beacon Keepers*, persists: repair a lighthouse, help ferry crews and choose how to ration fuel. Controls and objective are introduced before any generative technique. All fixtures and placeholder assets are invented for the book.

## Assessment edition
Needed: chapter checks, three exercises per chapter, worked solution traces, and the playable capstone with rubrics. Desired: tagged Canvas module design and trace-reading quizzes. Optional: compact glossary cards. Out of scope: certification and exam bank. Independently make the first design, request narrow AI assistance only if permitted, then verify against game state or tests; retain a Frictional log of rejected and changed output. Grade mechanics/constraints 35%, independent evidence 35%, rights/fallback decisions 20%, and handoff clarity 10%. Do not require cloud access or publication.
